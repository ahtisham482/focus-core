# Support decision — flagged for the owner, not scheduled

Roadmap 3.3 notes the support channel/SLA story is a **business
decision for the owner**, not engineering. This brief lays out the
options a solo maintainer can actually offer, what each costs, and a
recommendation. Nothing here is decided — pick one when a customer
asks for it.

## Option A — Community support only (recommended for now)

- **What:** GitHub Issues on the public repo, answered best-effort.
  No promised response time, no SLA, no private channel.
- **Cost to you:** near zero — answer when you have time.
- **Risk:** an enterprise buyer doing vendor review may ask "who do we
  call when it breaks?" The honest answer today is "the issue tracker".
  For a free/local-first tool at this stage, that is normal and fine.

## Option B — Email support with a stated response time

- **What:** a support address (even a Gmail) with a public promise,
  e.g. "we reply within 2 business days". Still no SLA penalties —
  just a stated expectation.
- **Cost to you:** 1–3 hours a week once users arrive; the promise
  creates pressure on days you are busy with client work.
- **When it makes sense:** the first time a real user (not a friend)
  says "I need to know someone will answer".

## Option C — Paid priority support

- **What:** a paid tier with faster response for fleet customers.
- **Cost to you:** billing, invoicing, tax questions, and the admin
  overhead of tracking who paid for what — work you do not have
  today. Do not build this before someone offers money for it.

## Recommendation

**Stay on Option A, and say so plainly.** Put one line in the admin
guide: "Support is through GitHub Issues; there is no SLA." That
honesty is better than a vague promise. Move to B only when a real
user asks for a response-time commitment, and to C only when a
customer offers to pay.
